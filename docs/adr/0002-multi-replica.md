# ADR 0002：解除单副本限制

- 状态：已采纳
- 日期：2026-11-20
- 相关：`docs/adr/0001-runtime-choice.md`

## 背景

ADR 0001 确定的部署形态是单实例、无 Redis。这带来两个限制：

1. `public.runs` 的队列与 SSE 依赖进程内实现，第二个副本既看不到也接不住第一个副本的 run；
2. 工作流 run 的最终状态由一个进程内的轮询任务写入，副本挂掉后该 run 会永远停在 `running`。

## 决策

### 1. 打开 Aegra 的 Redis broker

设置 `REDIS_BROKER_ENABLED=true` + `REDIS_URL`，Aegra 的任务队列与 SSE pubsub 改走 Redis，任意副本都可以创建、执行、流式读取任意 thread 的 run。

我们自己的限流计数器复用同一个开关和同一个 Redis 连接，不引入第二个开关。

### 2. 工作流用「读时对账」而不是「跨副本接管」

要让 B 副本接管 A 副本留下的 run，B 必须能读那个 run 在运行时里的状态，而运行时的读接口按 `identity = app_id:user_id` 鉴权。只有三种做法：

| 方案 | 问题 |
|---|---|
| 保存用户 Token | 明文凭证落库，不可接受 |
| 服务级万能凭证 | 泄漏即全租户冒充，破坏「不信任头部」这条底线 |
| 直接读 `public.runs` | 绕过运行时边界，和 Aegra 内部 schema 强耦合 |

三者都不划算。改为：**任何一次读状态，都用调用方自己的凭证向运行时对账**，发现终态就落库。于是：

- 不需要服务级凭证，权限模型不变；
- 任意副本都能服务任意 run 的状态与结果；
- 轮询任务变成「加速器」而非「唯一写入者」，它挂了不会丢 run；
- 顺带修掉单副本下的老问题：轮询任务异常退出后 run 卡死。

超时也由读时对账兜底（按 `created_at + WORKFLOW_RUN_TIMEOUT_SECONDS` 判定），不再依赖轮询任务存活。

### 3. 启动时不再批量标记 `interrupted`

原实现会在启动时把所有 `pending`/`running` 标成 `interrupted`。多副本下这是错的——它会杀掉别的副本正在跑的 run。该逻辑已删除，改为：未完成的 run 由下一次读对账收敛（运行时还在跑就继续跑，运行时丢了就判 `failed: runtime_lost`）。

### 4. 配额用 Redis 计数器，Redis 不可用时降级

每应用每分钟请求数、每日请求数用固定窗口 `INCR + EXPIRE` 计数。Redis 不可用时降级为进程内计数并记一条告警：**限流是保护性措施，不能因为它自己故障而拒绝全部业务流量**，所以选择降级而不是失败关闭。代价是多副本下实际阈值会放宽到 `limit × 副本数`。

## 后果

- `docker-compose.yml` 增加 `redis:7-alpine`，`--maxmemory-policy noeviction`（队列键被淘汰等于丢任务）。
- 多副本部署必须先去掉 `ports` 映射（两个副本无法绑定同一个宿主端口），由反代指向服务名。
- `workflow_runs.heartbeat_at` 记录「最后一次被轮询观察」的时间。它不再参与接管判定，只作为运维信号：`running` 且心跳陈旧 = 轮询者已死，下一次读会收敛它。
- 进程正常关闭时不再把在跑的 run 标记为 `interrupted`，这与「多副本下不能替别人做决定」一致。
